# Security Policy

## Reporting a concern

If you discover a sensitive disclosure issue, an accidentally published private artifact, or a release-safety problem in this repository, please use GitHub's private security reporting flow if available instead of opening a public issue first.

If private reporting is not available in your environment, contact the maintainer directly before posting details publicly.

## What belongs in a security report

Useful reports include:

- accidentally exposed local paths, usernames, or machine-specific details
- credentials, tokens, or endpoints that should not be public
- release artifacts that appear to contain restricted or non-public material
- workflow issues that could mislead external users about what is safe to run or publish

## What does not need a private report

Normal benchmark bugs, documentation fixes, reproducibility issues, and evaluation disagreements should go through the standard issue or pull request flow.

## Response goals

The aim is to review credible release-safety reports quickly, remove or quarantine sensitive material when needed, and document the fix once it is safe to do so.
